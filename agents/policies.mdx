A policy is data, not code. It always terminates, it is validated when you write it rather than
when an agent is waiting, it diffs in review, and any UI can render it. A policy engine standing
in front of money should be analysable, not Turing-complete.

## Your first policy

A policy carries two things: **typed columns** for the common cases, and a general **`rules`
array** for everything else. The columns are shorthand that compiles into the same rules, so use
them when they fit.

```bash
curl -X POST https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/policies \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{
    \"runtime_id\": \"$KORDIO_RUNTIME_ID\",
    \"per_transaction_cap_cents\": 50000,
    \"approval_threshold_cents\": 20000,
    \"velocity_cap_cents\": 200000,
    \"velocity_window_seconds\": 3600
  }"
```

Never more than $500 in one action, hold anything over $200 for a person, and never more than
$2,000 in any rolling hour. The third rule is the one that catches a retry loop.

### The typed columns, and the rule name each produces

This mapping matters, because the name you see in `decision.rule` is **not** the underlying
rule kind:

| Column | Compiles to | `decision.rule` |
| --- | --- | --- |
| `per_transaction_cap_cents` | `cost_cap` | `per_transaction_cap` |
| `velocity_cap_cents` + `velocity_window_seconds` | `spend_window` | `velocity_cap` |
| `monthly_cap_cents` | `monthly_spend_cap` | `monthly_cap` |
| `approval_threshold_cents` | `approval_threshold` | `approval_threshold` |
| `counterparty_allowlist` | `resource_allowlist` | `counterparty_allowlist` |

Write the same limit in the `rules` array instead and it reports under its `rule_name`, which
defaults to the kind. Both are fine; just do not expect a cap set through
`per_transaction_cap_cents` to come back as `cost_cap`.

## Rule kinds

| Kind | Settings | What it does |
| --- | --- | --- |
| `cost_cap` | `max_cents` | Refuses a single action above the ceiling. |
| `spend_window` | `max_cents`, `window_seconds` | Refuses once spend in a rolling window exceeds the cap. |
| `monthly_spend_cap` | `max_cents` | Refuses once calendar-month spend exceeds the cap. |
| `rate_limit` | `max_actions`, `window_seconds` | Refuses on count rather than amount. Catches loops that spend nothing per call. |
| `approval_threshold` | `above_cents` | Holds for a person instead of refusing. |
| `action_allowlist` | `allow` | Only these action types are permitted. |
| `resource_allowlist` | `allow` | Only these counterparties or resources are permitted. |
| `condition` | `when`, `effect` | A boolean expression over the action. |

Every kind takes an optional `rule_name`, echoed back in the decision, and every kind except
`action_allowlist` takes an optional `action_types` array to scope it; an empty array means all
action types. Every rule is assigned a stable `id` on write, so a decision read months later can
still name the exact rule that produced it.

An unknown kind, or a missing setting, is rejected when the policy is written. Never when an
agent is waiting on an answer.

<Note>
  An `allow` array that is empty is a no-op, not a deny-all. To deny by default, use
  `mode: "allowlist"` instead.
</Note>

Window rules count both action intents in `pending`, `requires_approval` or `completed`, and
payment intents in `pending`, `requires_approval`, `executed` or `settled`. Spend on one
consumes the other's headroom.

## The condition language

`condition` is the open one: a boolean expression over the action, with an effect.

```json
{
  "kind": "condition",
  "effect": "deny",
  "rule_name": "engineering_vendors_only",
  "when": {
    "all_of": [
      {"field": "action_type", "operator": "starts_with", "value": "payment."},
      {"any_of": [
        {"field": "resource", "operator": "in", "value": ["api.openai.com", "api.anthropic.com"]},
        {"field": "metadata.preapproved", "operator": "eq", "value": true}
      ]},
      {"not": {"field": "cost_cents", "operator": "gt", "value": 50000}}
    ]
  }
}
```

**Effects** are `deny` (the default), `allow`, or `require_approval`.

**Combinators** are `all_of`, `any_of` and `not`, nestable to ten levels. An empty `all_of` or
`any_of` is rejected at write time.

**Fields** are `action_type`, `resource`, `cost_cents`, `currency`, `runtime_id`,
`runtime_mode`, `session_id`, and any `metadata.*` dot path.

**Operators** are `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `contains`,
`starts_with`, `ends_with`, `exists`.

A missing field never raises; it simply fails to match. Unknown fields and operators are
rejected at write time.

<Note>
  The ordered comparisons (`gt`, `gte`, `lt`, `lte`) are numeric. A non-numeric operand makes
  the comparison `false` rather than an error, so a typo in a `metadata.*` path silently fails to
  match rather than blowing up. Use `exists` when you need to distinguish "absent" from
  "false".
</Note>

## Blocklist and allowlist

A policy is `blocklist` by default: the action is permitted unless a rule denies it.

Set `mode: "allowlist"` and it inverts. The action is denied unless one of that policy's `allow`
rules matches, reported as the rule `not_allowlisted`. A `deny` rule still overrides an `allow`.

Each allowlist policy is an independent gate. Attach two and both must be satisfied.

<Warning>
  Allowlist mode is the right default for a runtime that touches real money. Start by denying
  everything and naming what you permit, rather than trying to enumerate every way an agent
  could go wrong.
</Warning>

## Reusable modules

Modules are named rule sets scoped to a workspace. A policy imports them by name and they
compile in ahead of its own rules.

```bash
curl -X POST https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/policy_modules \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "vendor-allowlist", "rules": [
        {"kind": "resource_allowlist", "allow": ["acme-supplies.example"]}
      ]}'
```

```json
{ "runtime_id": "7d2a...", "imports": ["vendor-allowlist"], "rules": [] }
```

Modules are addressed by `name`, not by id, so `GET /v1/workspaces/{slug}/policy_modules/vendor-allowlist`
reads one back.

Editing a module changes every policy importing it. A policy importing an unknown module will
not save, and a module still imported by a policy will not delete. Modules do not import other
modules, so composition is one level deep and cannot cycle.

## Test before you apply

Never guess what a policy does. Preview a draft you have not saved:

```bash
curl -X POST https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/policy_previews \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{
    \"runtime_id\": \"$KORDIO_RUNTIME_ID\",
    \"action_type\": \"payment.create\",
    \"cost_cents\": 75000,
    \"policy\": { \"per_transaction_cap_cents\": 50000 }
  }"
```

```json 200 OK
{
  "data": {
    "outcome": "denied",
    "rule": "per_transaction_cap",
    "detail": { "max_cents": 50000, "requested_cents": 75000 },
    "headroom": { "per_action_cap_cents": 50000 },
    "policy_snapshot": []
  }
}
```

Nothing is persisted: no policy, no session, no intent, no audit event. `imports` resolve
against the workspace's real saved modules, so you can preview a draft that builds on modules
already in place. `session_budget_cents` sets the synthetic session budget and defaults to
`100000`.

Previewing needs only the `read` capability, deliberately: it is not a mutation.

The same evaluation is available to your agent at `POST /v1/agent/actions/simulate`, which does
record an `action.simulated` audit event.
