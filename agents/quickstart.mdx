By the end of this page an agent of yours asks Kordio before it spends, and Kordio answers
`allowed`, `requires_approval`, or `denied`, naming the rule that decided.

<Info>
  **Wrong page?** This gates what an agent is allowed to spend, before it spends it. If you are
  here to post double-entry transactions and read balances, you want the [Ledger
  quickstart](/ledger/quickstart) instead.
</Info>

Everything here runs in test mode, which uses the same policy engine as live, so the
integration you write now is the one you ship.

## 0. Get your credentials

Sign up at [app.kordio.io](https://app.kordio.io), create a workspace, and mint a dashboard
token. The full walkthrough is on [getting your
credentials](/agents/authentication#getting-your-credentials).

<Snippet file="env-agents.mdx" />

## 1. Create an agent

An **agent** is a scoped identity for one workload. It carries its own API key and its
own permitted action types.

```bash
AGENT=$(curl -s -X POST \
  https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/agents \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"procurement agent","mode":"test","scopes":["payment.*","tool.invoke"]}')

export KORDIO_AGENT_ID=$(echo "$AGENT" | jq -r '.data.id')
export KORDIO_AGENT_KEY=$(echo "$AGENT" | jq -r '.data.api_key')
```

`api_key` is returned exactly once and starts with `krt_test_`. Store it the way you store any
other secret; Kordio keeps only a digest and cannot show it to you again.

<Warning>
  `scopes` restricts which action types this key may even ask about. An empty array means
  unrestricted. Prefer one agent per agent workload with the narrowest scopes that work.
</Warning>

## 2. Write a policy

**Do not skip this step.** An agent with no active policy denies everything, with the rule
`no_policy`. That is deliberate and fail-closed: an agent nobody has written rules for has no
authority, rather than unlimited authority.

```bash
curl -X POST https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/policies \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{
    \"agent_id\": \"$KORDIO_AGENT_ID\",
    \"per_transaction_cap_cents\": 50000,
    \"approval_threshold_cents\": 200000,
    \"velocity_cap_cents\": 200000,
    \"velocity_window_seconds\": 3600
  }"
```

That policy says: never more than $500 in one action, hold anything over $2,000 for a person,
and never more than $2,000 in any rolling hour.

The third rule is the one that catches a retry loop. The first two, on their own, would let
nineteen individually reasonable $340 charges through.

## 3. Open a budget

A **budget** is a budget envelope for one run. Spend is committed against it, and it is the
unit that stops a loop rather than a single mistake.

<CodeGroup>

```bash cURL
BUDGET=$(curl -s -X POST https://api.kordio.io/v1/agent/budgets \
  -H "Authorization: Bearer $KORDIO_AGENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"budget_cents": 50000, "currency": "USD"}')

export KORDIO_BUDGET_ID=$(echo "$BUDGET" | jq -r '.data.id')
```

```typescript TypeScript
const res = await fetch("https://api.kordio.io/v1/agent/budgets", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.KORDIO_AGENT_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ budget_cents: 50_000, currency: "USD" }),
});
const { data: budget } = await res.json();
```

```python Python
import os, requests

res = requests.post(
    "https://api.kordio.io/v1/agent/budgets",
    headers={"Authorization": f"Bearer {os.environ['KORDIO_AGENT_KEY']}"},
    json={"budget_cents": 50_000, "currency": "USD"},
)
budget = res.json()["data"]
```

## 4. Ask before you spend

This is the call that matters. Put it in front of the action, not after it.

<CodeGroup>

```bash cURL
ACTION=$(curl -s -w '\n%{http_code}' -X POST https://api.kordio.io/v1/agent/actions \
  -H "Authorization: Bearer $KORDIO_AGENT_KEY" \
  -H "Idempotency-Key: order-4471-attempt-1" \
  -H "Content-Type: application/json" \
  -d "{
    \"budget_id\": \"$KORDIO_BUDGET_ID\",
    \"action_type\": \"payment.create\",
    \"resource\": \"acme-supplies.example\",
    \"cost_cents\": 12000
  }")

export KORDIO_ACTION_ID=$(echo "$ACTION" | head -n-1 | jq -r '.data.id')
echo "$ACTION" | tail -n1   # the status code you branch on
```

```typescript TypeScript
const res = await fetch("https://api.kordio.io/v1/agent/actions", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.KORDIO_AGENT_KEY}`,
    "Idempotency-Key": "order-4471-attempt-1",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    budget_id: budget.id,
    action_type: "payment.create",
    resource: "acme-supplies.example",
    cost_cents: 12_000,
  }),
});

const body = await res.json();
switch (res.status) {
  case 201: /* execute, then report in step 5 */ break;
  case 202: /* held for a person. stop and wait */ break;
  case 403: /* denied. do not execute */ break;
}
```

```python Python
res = requests.post(
    "https://api.kordio.io/v1/agent/actions",
    headers={
        "Authorization": f"Bearer {os.environ['KORDIO_AGENT_KEY']}",
        "Idempotency-Key": "order-4471-attempt-1",
    },
    json={
        "budget_id": budget["id"],
        "action_type": "payment.create",
        "resource": "acme-supplies.example",
        "cost_cents": 12_000,
    },
)
body = res.json()
# 201 execute · 202 held for a person · 403 denied
```

Read the status code, not the body, to branch:

| Status | Outcome | What your agent does |
| --- | --- | --- |
| `201` | `allowed` | Execute, then report the result in step 5. |
| `202` | `requires_approval` | Stop. A person has to resolve it. Poll `GET /v1/agent/actions/{id}` or wait for your webhook. |
| `403` | `denied` | Do not execute. `decision.rule` names what refused. |

`Idempotency-Key` is required, and its absence is a `422`, not a `400`. Reuse the same key when
you retry and Kordio replays the original decision instead of reserving the budget twice.

<Note>
  `decision.headroom` reports what is left on every limit that applied. Surface it to your
  agent so it can pick a cheaper path instead of retrying into the same wall.
</Note>

## 5. Report what happened

Kordio holds the budget reservation until you say how the action ended.

```bash
curl -X POST \
  https://api.kordio.io/v1/agent/actions/$KORDIO_ACTION_ID/complete \
  -H "Authorization: Bearer $KORDIO_AGENT_KEY"
```

If it failed, say so instead. The reservation is released and the budget goes back:

```bash
curl -X POST \
  https://api.kordio.io/v1/agent/actions/$KORDIO_ACTION_ID/fail \
  -H "Authorization: Bearer $KORDIO_AGENT_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason": "vendor returned 502"}'
```

Skipping this step is the most common integration mistake. An action that is never completed
or failed holds its budget until the budget closes.

<Note>
  Payments report the same way, through
  `POST /v1/agent/payment_intents/:id/complete` and `/fail`. Kordio authorizes the spend and
  hands you a cosignature; your own rail moves the money. See [the payments
  section](/agents/concepts#payments-work-like-actions).
</Note>

## 6. Try it without spending anything

`simulate` runs the whole policy evaluation and records no intent and no reservation. Use it in
tests, and in your own UI to show someone what a policy would do before they save it.

```bash
curl -X POST https://api.kordio.io/v1/agent/actions/simulate \
  -H "Authorization: Bearer $KORDIO_AGENT_KEY" \
  -H "Content-Type: application/json" \
  -d "{
    \"budget_id\": \"$KORDIO_BUDGET_ID\",
    \"action_type\": \"payment.create\",
    \"cost_cents\": 999999
  }"
```

```json 200 OK
{
  "data": {
    "outcome": "denied",
    "rule": "session_budget",
    "detail": { "requested_cents": 999999, "remaining_cents": 38000 },
    "headroom": { "session_remaining_cents": 38000 },
    "policy_snapshot": []
  }
}
```

It always returns `200`, whatever the outcome, and the decision has no `id` because no intent
was created.
