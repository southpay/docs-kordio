The control layer answers one question, and it answers it the same way for a payment, a paid tool call, or anything else an agent asks for:

> May this runtime take this action, right now?

An action is `(runtime, session, action_type, resource, cost_cents)`. A decision is `allowed`, `requires_approval`, or `denied`, and it carries the rule that produced it plus the remaining headroom on every limit that applied.

## The five primitives

  <Card title="Session" icon="timer">

  </Card>
  <Card title="Policy" icon="scale">
    The rules attached to a runtime. Caps, windows, allowlists, approval thresholds, and a condition language for everything else.
  </Card>
  <Card title="Intent" icon="file-check">
    The record of one decision: what was asked, what was decided, which rule decided it, and what happened next.

The fifth is the **cosignature**: a short-lived signature over an allowed decision, so whoever executes the action can verify the authority without calling us. That one has [its own page](/agents/cosignatures).

## Why a session and not just a cap

A per-transaction cap stops one big mistake. It does nothing about the same reasonable-looking action happening nineteen times.

A session is the answer to that. You open one per run with a budget, every authorized action commits against it, and the budget is what a loop runs into. Reservations are held while an action is pending or waiting on a person, and released when it fails or is denied, so a crashed agent does not strand its budget forever.

Budget is claimed with a single conditional update rather than a lock, so parallel sub-agents under one runtime contend at the row instead of queueing behind each other.

## How a decision is reached

Three intrinsic rules always run first:

1. The session must be active.
2. The runtime's key must be scoped for this action type.
3. The spend must fit the remaining session budget.

Then the rules compiled from each active policy run. **The first denial wins.** An approval requirement only stands if nothing denies. That ordering matters: a rule that would hold something for a human never overrides a rule that refuses it outright.

Every decision carries `headroom`, which reports what is left on each limit that applied. Give it to your agent. An agent that knows it has $380 left on the session picks a cheaper vendor; an agent that only knows it was refused retries into the same wall.

## Test and live mode

A runtime is `test` or `live`. Both run the same engine, evaluate the same policies, and return the same shapes, including cosignatures. The difference is that live runtimes authorize real money and require a paid plan.

This means you can prove the entire integration, including cosignature verification inside your own executor, before anything is at stake.

## What Kordio never does

Kordio holds no funds, no accounts, and none of your credentials. It decides and it signs; your own rails and your own keys execute.

That is a deliberate limit, and it has a consequence worth stating plainly: an executor that never checks with Kordio and never verifies a cosignature is not governed by it. The control layer binds the paths you route through it. Put the check in front of the spend, in code your agent cannot skip, and verify the signature where the action is actually carried out.

## Where the ledger fits

Every reservation the control layer takes is mirrored into a double-entry ledger, so decisions become balanced postings your finance team can reconcile. Each workspace owns its own books and each runtime owns an account inside them.

The projection never sits in the authorization path. A slow or unavailable ledger can delay a posting; it can never delay or change a decision.
