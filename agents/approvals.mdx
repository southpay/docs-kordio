Some spend should not be a machine's call. An approval threshold does not refuse the action; it
parks it until a person decides.

## What your agent sees

When a rule holds an action, the authorize call returns `202` and the intent is in state
`requires_approval`:

```json 202 Accepted
{
  "data": {
    "id": "9b2ef0c1-6a3d-4e75-8c19-2f4b7d5a0e63",
    "state": "requires_approval",
    "action_type": "payment.create",
    "cost_cents": 240000,
    "currency": "USD"
  },
  "decision": {
    "outcome": "requires_approval",
    "rule": "approval_threshold",
    "detail": { "above_cents": 100000 },
    "headroom": { "session_remaining_cents": 260000 },
    "policy_snapshot": []
  }
}
```

There is no `cosignature`. Nothing has been authorized yet.

The budget is reserved while the intent waits, so a held action cannot be quietly outspent by
the next one.

## How your agent should wait

Do not busy-poll, and do not treat a hold as a failure to retry around. Retrying with a new
idempotency key creates a second held intent and asks a person the same question twice.

## What the person sees

An approver who only sees "approve $2,400?" is rubber-stamping. So there is an endpoint that
answers what approving would actually do, before anyone clicks:

```bash
curl "https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/action_intents/$KORDIO_ACTION_ID/impact" \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN"
```

```json 200 OK
{
  "data": {
    "amount_cents": 240000,
    "currency": "USD",
    "rule": "approval_threshold",
    "executed": false,
    "session": {
      "id": "3f1c8a92-5d41-4c8e-9f2b-7a6e1d0c4b83",
      "budget_cents": 500000,
      "spent_cents": 240000,
      "remaining_cents": 260000,
      "returns_on_deny_cents": 240000,
      "open_holds": 2
    },
    "runtime": {
      "id": "7d2a6c15-3f89-4b02-9e64-8a15d7c0b3f2",
      "name": "procurement agent",
      "mode": "live",
      "scopes": ["payment.*"]
    },
    "windows": [
      { "kind": "velocity", "window_seconds": 3600, "cap_cents": 500000,
        "spent_cents": 240000, "remaining_cents": 260000 }
    ],
    "spend_token": null
  }
}
```

Two figures are worth reading carefully. Budget is **already reserved** while an intent is held,
so approving costs no further headroom — `returns_on_deny_cents` is what denying gives back. And
`open_holds` counts every other held intent competing for the same session budget, which is how
an approver sees that three pending approvals total more than the session can cover.

`GET .../payment_intents/{id}/impact` is the same shape, plus the spend token the payment cites,
if any.

## Resolving it

```bash
curl -X POST \
  "https://api.kordio.io/v1/workspaces/$KORDIO_WORKSPACE/action_intents/$KORDIO_ACTION_ID/approve" \
  -H "Authorization: Bearer $KORDIO_DASHBOARD_TOKEN"
```

Both calls require the `approve` capability, and both record `resolved_by_sub` — who decided —
and emit `approval.resolved`.

### Actions and payments resolve differently

This asymmetry is the one to get right:

| | Action intent | Payment intent |
| --- | --- | --- |
| **Approved** | Moves to `pending`. Your agent proceeds as it would have on a `201`, then reports with `complete` or `fail`. | **Executed immediately**, in the approve request. Comes back `executed` or `failed`. Nothing left for the agent to do. |
| **Denied** | Moves to `denied`, reservation released. | Moves to `denied`, reservation released, ledger release enqueued. |

Approving an action grants authority. Approving a payment *is* the execution.

<Warning>
  A denial is not a rate limit. Do not re-ask with a fresh idempotency key. If your agent
  genuinely needs a different action, that is a different action: new amount, new resource, new
  key.
</Warning>

Resolving an intent that is not in `requires_approval` is a `422`, so a double-click cannot
double-execute.

## Who can approve

Approving is a capability, not a job title. `approve` is separate from `manage_policy`, so the
person who authorises a payment need not be the person who can widen the rule that held it.

Keep those apart. Segregation of duties is most of what an auditor is looking for here, and it
is the reason approvers are unlimited on every paid plan: capping the people allowed to approve
spend would make holds sit longer and agents stall.
