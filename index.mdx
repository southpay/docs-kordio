## What Kordio is

Kordio is the control layer for AI agents that spend. Before an agent pays a vendor or calls a paid tool, it asks Kordio. We evaluate the action against policy you wrote and answer in the same request: allowed, requires approval, or denied, naming the rule that decided and reporting the headroom left on every limit.

Every allowed decision comes back signed, so whatever executes the action can verify the authority instead of trusting the agent. We hold no funds, no accounts, and none of your credentials. A required signer, never a custodian.

Underneath sits a double-entry ledger that records every decision as balanced postings. It is included rather than sold separately, and it is documented in its own right further down, because plenty of teams want the books on their own terms.

## The ledger underneath

You model accounts, post balanced transactions, and read balances over a plain HTTP API. The ledger guarantees the accounting invariants; you write the business logic.

You sign up, get OAuth client credentials, and ship in minutes. There is no sales call and no setup project. You get primitives, not opinions: the platform never bakes in your domain, so a treasury startup, a marketplace, an FX desk, and a SaaS company billing its own usage all use the same four primitives.

<Info>
  The control layer is one customer of this ledger. The ledger itself knows nothing about agents. It speaks accounts, postings, transactions, and balances.
</Info>

## The mental model

Four primitives cover the whole API.

<CardGroup cols={2}>
  <Card title="Account" icon="wallet">
    A named bucket of value in one currency. You choose the `id` and `currency`, and both are immutable once set.
  </Card>
  <Card title="Posting" icon="arrow-right-left">
    One line of a transaction. It says: this account moved by this amount in this direction (`debit` or `credit`).
  </Card>
  <Card title="Transaction" icon="layers">
    A set of postings that move together. The ledger enforces `sum(debits) == sum(credits)` per currency. That is the whole correctness model.
  </Card>
  <Card title="Balance" icon="scale">
    The net of an account's postings, current or at a historical instant. Computed from `value_date`, never recomputed from market data.
  </Card>
</CardGroup>

## A balanced transaction

A transaction is correct when its debits equal its credits in every currency it touches. The simplest case moves value between two accounts:

```json
{
  "postings": [
    { "account": "cash:usd", "amount": "1000", "currency": "USD", "direction": "debit" },
    { "account": "revenue:subscriptions", "amount": "1000", "currency": "USD", "direction": "credit" }
  ]
}
```

The ledger rejects anything that does not balance. Amounts are integers in the currency's minor units (cents for `USD`, satoshis for `BTC`), so there are no floating-point rounding surprises.

<Warning>
  Monetary values cross the wire as JSON **strings** of integer minor units (`"1000"`, not `1000`). This keeps 18-decimal token amounts that exceed `2^53` exact. Parse money with a big-integer or decimal type, never a JS `number`. On write, `amount` accepts an integer or a string; reads always return a string. See [Core concepts](/concepts#integer-minor-units).
</Warning>

## What makes it safe

<CardGroup cols={2}>
  <Card title="Append-only" icon="lock">
    Postings are never edited. You correct mistakes with a reversal or a refund, which are new transactions that reference the original.
  </Card>
  <Card title="Idempotent" icon="rotate-cw">
    Every write carries an `Idempotency-Key`. A replay returns the original transaction instead of writing a duplicate.
  </Card>
  <Card title="Multi-currency" icon="coins">
    Currency is first class. No code path assumes a single currency, and balances are tracked per currency.
  </Card>
  <Card title="Test and live modes" icon="flask-conical">
    Each OAuth client is bound to a mode. The mode of your token decides whether you read and write test or live data. They never mix.
  </Card>
</CardGroup>
